# Этап 0. Каркас и конвейер проверок

Статус: **реализовано, ждёт проверки на машине ALEX.**
Ветка `stage-0`, коммит `39a41ba`. Локально проверено: Pint, PHPStan (уровень 6),
PHPUnit (7 тестов, 25 утверждений), `npm ci` + `npm run build`, идемпотентность
генератора `.env`. Сборка `stack` проверяется только в GitHub Actions —
доступа к docker-демону из среды Cowork нет.
Источник этапов — `docs/roadmap-v2.md`, часть 5. Требования к продукту — `docs/requirements.md`.

**Цель этапа:** получить возможность выполнять и проверять код. Ни одной строки
предметной логики. Пока этого нет, всё остальное — косметика: пять дефектов
из двенадцати в первой версии возникли ровно потому, что код ни разу не был
запущен до передачи.

## 0.1. Зафиксированные версии

Проверено 29 августа 2026 по официальной странице релизов Laravel, а не по памяти —
именно неверное предположение о версии дало дефект №1.

| Компонент | Версия | Почему |
|---|---|---|
| PHP | **8.4** | Laravel 13 требует 8.3–8.5. 8.4 — середина диапазона, безопасностные исправления дольше, чем у 8.3 |
| Laravel | **13.x** | Вышел в Q1 2026, исправления ошибок до Q3 2027, безопасность до Q1 2028. Laravel 12 вышел из окна исправления ошибок 13 августа 2026 |
| MySQL | **8.4 LTS** | Долгая поддержка. `default-authentication-plugin` в ней удалена — см. запрет в `docker/mysql/my.cnf` |
| nginx | 1.27-alpine | |
| Node | 22-alpine | сборка фронтенда |
| Vue / Vite / Pinia / Chart.js | как в `frontend/package.json` | фронтенд переносится без изменений |

Версии образов в `docker-compose.yml` закрепляются тегом, `latest` не используется нигде.

## 0.3. Объём этапа

### A. Репозиторий

- Ветка `main` защищена: прямой пуш запрещён, изменения приезжают только через pull request.
- Один этап — один pull request с зелёным CI.
- `ODDS_API_KEY` кладётся в Secrets репозитория (понадобится с этапа 4; на этапе 0 — только проверка, что переменная читается и маскируется в логах).

### B. Каркас бекенда

Скелет Laravel 13 без единого класса предметной области. В нём:

- `GET /up` — штатная проверка Laravel, отвечает 200.
- `GET /api/health` — свой эндпоинт: возвращает JSON с версией PHP, версией Laravel,
  признаком доступности БД и текущим временем. Это то, что дёргает `make doctor` и сборка `stack`.
- Middleware, принудительно отдающий JSON на всё, что под `/api`.
- Один юнит-тест `SmokeTest`, который заведомо проходит, и один намеренно
  проверяющий соединение с БД функциональный тест на SQLite.
- `phpunit.xml` с двумя наборами: `Unit` (без БД) и `Feature` (SQLite в памяти).

Предметных таблиц нет — только служебные миграции Laravel. Схема БД появится на этапе 2.

### C. Фронтенд

Переносится из первой версии без изменений кода. Добавляется только:

- `npm run build` обязан проходить в CI на чистом `npm ci`;
- `frontend/package-lock.json` фиксируется и коммитится;
- `frontend/dist/` **удаляется из репозитория** и добавляется в `.gitignore` —
  собранные файлы в git приводят к тому, что рассинхрон сборки и исходников
  замечается поздно. Сборку делает `make front` или контейнер `node`.

### D. Docker

Файлы переносятся, вносятся правки:

1. **`docker-compose.yml`** — внешний порт MySQL больше не меняет умолчание под работающей
   системой (дефект №6). Правило: значение пишется явно в корневой `.env` командой
   `make setup` при первой настройке и после этого не трогается никогда.
   В `docker-compose.yml` умолчание остаётся `33061` — тем же, что было на момент,
   когда подключение в PhpStorm настраивалось и работало.
2. **`docker/mysql/my.cnf`** — запрет на `default-authentication-plugin` остаётся
   с комментарием (дефект №2). Проверяется сборкой `stack`: контейнер обязан стать healthy.
3. **`docker/php/entrypoint.sh`** — правило «разовая команда исполняется молча»
   сохраняется (дефект №9). Добавляется автотест в сборке `stack`:
   `docker compose exec -T php php -v` обязан выдать ровно вывод `php -v`
   и ничего больше — первая строка начинается с `PHP `.
4. **`docker/php/Dockerfile`** — Xdebug ставится в образ всегда, включается только
   переменной `XDEBUG_MODE`. `make debug-on` пересобирает образ, а не только
   перезапускает контейнер (дефект №8), и проверяется командой `make debug-check`.

### E. Makefile

Набор команд этапа 0 (остальные добавляются по мере появления функций):

| Команда | Что делает |
|---|---|
| `make setup` | первая настройка: создаёт корневой `.env`, **дописывая недостающие ключи и никогда не перезаписывая существующие** (дефект №7), собирает фронт, поднимает контейнеры |
| `make up` / `make down` / `make restart` / `make rebuild` | управление контейнерами |
| `make doctor` | диагностика, см. ниже |
| `make db-info` | печатает параметры подключения для PhpStorm — хост, порт, база, пользователь (дефект №5) |
| `make test` | все тесты бекенда внутри контейнера |
| `make front` | сборка фронтенда |
| `make debug-on` / `make debug-off` / `make debug-check` | Xdebug |
| `make logs` / `make ps` / `make shell` / `make mysql` | эксплуатация |
| `make reset` | остановить всё и удалить том БД |

Правило для всех генераторов конфигов: **только дописывают, никогда не перезаписывают.**

### F. `make doctor`

Минимальная версия этапа 0. Печатает и проверяет:

1. Docker установлен и демон отвечает.
2. Все четыре контейнера подняты, MySQL — healthy.
3. Внешний порт MySQL из корневого `.env` действительно слушается, и по нему проходит
   соединение под пользователем приложения. Печатает готовую строку для PhpStorm.
4. `http://localhost:<APP_PORT>/up` отдаёт 200.
5. `http://localhost:<APP_PORT>/api/health` отдаёт JSON, и в нём `database: true`.
6. `frontend/dist/index.html` существует и новее, чем последний изменённый файл в `frontend/src`.
7. `docker compose exec -T php php -v` выдаёт чистый вывод без посторонних строк.

Каждая проверка печатает `OK` или внятную причину и подсказку, что сделать.
Ненулевой код возврата при любой неудаче — это то, что позволит гонять `doctor` в CI.

### G. GitHub Actions

| Сборка | Триггер | Что делает |
|---|---|---|
| `backend` | push, pull request | `composer install`, статический анализ, `phpunit` на SQLite |
| `frontend` | push, pull request | `npm ci`, `npm run build` |
| `stack` | push, pull request | собирает образы, поднимает Compose, ждёт готовности, накатывает миграции, дёргает `/up` и `/api/health`, прогоняет `tools/doctor.sh` |
| `contract` | по расписанию раз в сутки, а также на pull request, если правят её саму | на этапе 0 — заглушка, которая проверяет доступность источников в той мере, в какой их видно из GitHub Actions; наполняется на этапах 3 и 4 |

Сборка `stack` — главная: она ловит дефекты 2, 8 и 9 автоматически, без вашего участия.

**Про ufc.com и адреса датацентров.** Измерено при доведении сборок до зелёного:
`https://www.ufc.com/events` отвечает **403** на запросы из GitHub Actions и из
двух других облаков; подмена User-Agent на браузерный не помогает. С домашнего
адреса сайт отдаётся обычным образом. Отсюда деление: сборка `contract`
засчитывает и 200, и 403 (её дело — что имя резолвится, TLS встаёт и сервер
отвечает), а то, что страница действительно отдаётся, проверяет восьмая проверка
`make doctor` — на машине, откуда потом пойдёт парсер этапа 3. Она печатает
«ВНИМАНИЕ», а не «НЕТ»: 403 с рабочей машины означает включённый VPN, а не
поломку системы.

Практический вывод для этапа 3: сбор турниров нельзя переносить в GitHub Actions
и вообще в облако. Он живёт там же, где приложение, — на вашей машине.

## 0.5. Какие дефекты первой версии этап закрывает механически

| № | Дефект | Механизм, который его больше не пропустит |
|---|---|---|
| 1 | Laravel вне окна поддержки | версия проверена по странице релизов; `composer install` в CI на каждом PR |
| 2 | MySQL падает из-за удалённой переменной | сборка `stack`: контейнер обязан стать healthy |
| 5 | порт БД не описан | `make db-info` и вывод `make doctor` |
| 6 | смена умолчания порта | порт пишется явно в `.env` при `make setup` и не меняется |
| 7 | `make env` перезаписывал `.env` | генератор только дописывает недостающие ключи |
| 8 | `make debug-on` не пересобирал образ | `make debug-check` + проверка в `stack` |
| 9 | entrypoint шумел в stdout | автопроверка «первая строка `php -v` начинается с `PHP `» |

Дефекты 3, 4, 10, 11, 12 относятся к предметной логике и закрываются на этапах 2–4.

## 0.6. Определение готовности

Этап считается сделанным, когда **все** пункты отмечены:

- [ ] все четыре сборки GitHub Actions зелёные;
- [ ] сборка `stack` поднимает приложение с нуля на чистой машине и получает 200 от `/up`;
- [ ] сборка `stack` получает от `/api/health` JSON с `database: true`;
- [ ] `make setup` на вашей машине даёт тот же результат, что CI;
- [ ] `make doctor` отрабатывает все восемь проверок и печатает параметры подключения;
- [ ] `make setup`, запущенный второй раз, не портит уже настроенный корневой `.env`;
- [ ] прямой пуш в `main` невозможен;
- [ ] `frontend/dist` отсутствует в git и собирается командой.
