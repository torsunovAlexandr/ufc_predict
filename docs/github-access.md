# Как выдать доступ к репозиторию

Два пути. Первый предпочтительнее — при нём секрет вообще не создаётся.

---

## Главное правило

**Не присылайте токен в чат.** Переписка сохраняется, и всё, что в неё попало,
считается скомпрометированным — ровно так вышло с ключом The Odds API.
Ниже описано, как передать токен, не показывая его.

---

## Путь 1. Подключить GitHub к аккаунту Claude — токен не нужен

В окружении, где я работаю, есть штатный механизм доступа к GitHub: при попытке
обратиться к API прокси отвечает «GitHub access to this repository is not enabled
for this session», то есть механизм существует, но для этого аккаунта не включён.

Когда он настроен, доступ выдаётся **выбором конкретных репозиториев** через
приложение GitHub — никакого личного токена создавать и хранить не нужно,
и отзывается доступ там же, одной кнопкой.

Настройка — в интерфейсе Claude, раздел подключений и интеграций.
Пошаговая инструкция: [Use the GitHub integration](https://support.claude.com/en/articles/10167454-use-the-github-integration).

После подключения скажите мне — я проверю доступ одной командой и, если
всё сработало, второй путь не понадобится.

## Путь 2. Fine-grained токен

Работает гарантированно. Секрет создаётся, но живёт ограниченно и отзывается
в один клик.

### Шаг 1. Создать токен

GitHub → Settings → Developer settings → Personal access tokens →
**Fine-grained tokens** → Generate new token.

| Поле | Значение |
|---|---|
| Repository access | **Only select repositories** → только репозиторий проекта |
| Expiration | 30–90 дней, не «no expiration» |

Права (Permissions → Repository permissions) — ровно эти, больше ничего:

| Право | Уровень | Зачем |
|---|---|---|
| Contents | Read and write | читать код и пушить ветки |
| Pull requests | Read and write | создавать PR с готовой работой |
| Workflows | Read and write | создавать и править файлы в `.github/workflows` |
| Actions | Read | читать результаты сборок |
| Metadata | Read | обязательное, выставляется само |

Прав на administration, secrets, packages, webhooks и на организацию **не нужно**.

### Шаг 2. Защитить ветку main

Settings → Branches → Add rule для `main`: требовать pull request и прохождение
проверок. Тогда я физически не смогу запушить в основную ветку — только
предложить PR, который вы просмотрите.

### Шаг 3. Передать токен, не показывая его

В папке проекта:

```bash
cd "Documents/ufc predict"
mkdir -p .secrets
echo ".secrets/" >> .gitignore
# вставьте токен в файл любым редактором, одной строкой, без пробелов
open -a TextEdit .secrets/gh-token
```

Или сразу из терминала, чтобы токен не остался в истории команд
(строка начинается с пробела — bash и zsh такие строки не запоминают):

```bash
 printf '%s' 'сюда_токен' > .secrets/gh-token && chmod 600 .secrets/gh-token
```

После этого напишите мне «токен на месте» — **не сам токен**. Я скопирую файл
в своё окружение и настрою git так, чтобы значение нигде не печаталось:
ни в выводе команд, ни в конфигурации репозитория.

### Шаг 4. Положить ключ API в секреты репозитория

`ODDS_API_KEY` — не в код и не в файл, а в Settings → Secrets and variables →
Actions → New repository secret. В сборках он подставляется из окружения,
в логах GitHub его маскирует, я его не вижу.

### Что происходит с токеном дальше

- Файл `.secrets/gh-token` остаётся у вас на диске и не попадает в репозиторий.
- В моём окружении он живёт до конца сессии — контейнер эфемерный.
- В новой сессии я прочитаю файл заново, вашего участия не потребуется.
- Отозвать в любой момент: GitHub → Settings → Developer settings → токен → Revoke.
  После этого я теряю доступ мгновенно.

## Что я смогу делать с доступом

- Клонировать репозиторий и создавать ветки.
- Пушить и открывать pull request с описанием изменений.
- Читать результаты сборок CI: какие тесты упали и с каким сообщением.
- Чинить и пушить снова — до зелёной сборки, без вашего участия.

Чего не смогу: слить PR в `main` при включённой защите ветки, менять настройки
репозитория, читать другие ваши репозитории, видеть содержимое секретов.

---

## Если хочется начать с минимального доверия

Можно сделать репозиторий **публичным** и не выдавать никаких прав вовсе:
код я буду писать в папку проекта как сейчас, вы сами коммитите и пушите,
CI отрабатывает, а результаты сборок вы показываете мне.

Это медленнее — цикл проверки требует вашего участия на каждом круге, — но
не требует ни токена, ни подключений. Для этого проекта публичность безопасна:
секретов в коде нет, ключ API лежит в секретах репозитория.
