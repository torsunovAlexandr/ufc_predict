# UFC Predict v2 — разбор, подход и ТЗ по этапам

Документ отвечает на три вопроса: почему первая версия дала столько ошибок,
как построить работу, чтобы их стало кратно меньше, и что именно делать
на каждом этапе.

Код по этому документу ещё не писался — это план.

---

## Часть 1. Разбор: что именно ломалось

За время работы над первой версией всплыло двенадцать дефектов. Полезно
разложить их не по симптомам, а по причинам.

| # | Дефект | Как проявился | Корневая причина |
|---|---|---|---|
| 1 | Laravel 11 вне окна поддержки | composer отказался ставить зависимости | Неверное предположение о внешнем мире |
| 2 | `default-authentication-plugin` удалена в MySQL 8.4 | контейнер БД в цикле перезапуска | Конфиг не был исполнен ни разу |
| 3 | Неоднозначная колонка `status` в SQL с join | 500 на дашборде | Тест существовал, но не запускался |
| 4 | Тест сигмоиды требовал непредставимого в double | падал тест | Тест не запускался |
| 5 | Порт БД наружу 33061, а не 3306 | connection refused из PhpStorm | Пробел в документации |
| 6 | Смена умолчания порта на 3306 | сломалось уже настроенное подключение | Изменение умолчания под работающей системой |
| 7 | `make env` перезаписывал корневой `.env` | терялись ручные настройки | То же самое |
| 8 | `make debug-on` не пересобирал образ | Xdebug не появлялся | Не проверено запуском |
| 9 | entrypoint печатал в stdout при `php -v` | PhpStorm не определял интерпретер | Не проверено запуском |
| 10 | Ничья маппилась в `moneyline`, читалась как `draw` | котировка сохранялась и не использовалась | Не проверено на реальных данных |
| 11 | Тотал 4.5 не поддерживался | котировки главных боёв игнорировались | Формат внешних данных не был изучен |
| 12 | Котировки сопоставлялись с одним турниром | ложные «не сопоставлено» | Ошибка проектирования |

### Сводка по причинам

| Причина | Дефектов |
|---|---|
| Код не был исполнен ни разу до передачи | 2, 3, 4, 8, 9 — **пять** |
| Неверные предположения о внешнем мире (версии, форматы, разметка) | 1, 10, 11 — **три** |
| Изменение умолчаний под работающей системой | 6, 7 — **два** |
| Ошибка проектирования | 12 — **одна** |
| Пробел в документации | 5 — **одна** |

### Главный вывод

Дело не в том, что приложение писалось целиком. Дело в том, что **ни одна строка
не была выполнена до того, как попала к вам**. В моей среде нет доступа
к packagist, npm и Docker Hub — значит, не было ни `composer install`, ни тестов,
ни сборки образа. Всё, что я мог, — проверить синтаксис и прогнать математику
модели чистым PHP. Показательно, что единственный слой, который ни разу
не сломался, — это как раз ядро модели: только его я мог исполнять.

Размер первого шага усугубил проблему, но не создал её. Если писать по частям,
но по-прежнему вслепую, ошибки просто размажутся по этапам. Поэтому порядок
приоритетов такой:

1. **Сначала — возможность исполнять код.** Без этого остальное косметика.
2. Потом — деление на этапы, чтобы ошибка не расползалась и была локализуема.
3. Потом — фиксация реальных внешних данных, чтобы не гадать о форматах.

## Часть 2. Какие доступы дать, чтобы я проверял сам

Я замерил, что реально доступно из моей среды. Результаты ниже — факты,
а не предположения.

| Ресурс | Статус | Проверено |
|---|---|---|
| GitHub: `git clone` / `push` | **работает** | `git clone` публичного репозитория прошёл |
| GitHub REST API (`api.github.com`) | **работает** | код ответа 200 |
| Чтение веб-страниц через WebFetch | **работает** | прочитал ufc.com/events, вижу «UFC Shanghai — Nurmagomedov vs Song, 29 августа» |
| packagist.org | заблокирован | код 000, отказ прокси |
| registry.npmjs.org | заблокирован | код 403 |
| Docker Hub | заблокирован | код 000, отказ прокси |
| Прямые запросы к ufc.com, the-odds-api.com | заблокированы | код 000 |
| Встроенный браузер | доступен, требует разрешения на сайт | разрешение выдано, страница не открылась — требует разбирательства |
| Linux-VM на вашем Маке (`device_bash`) | нет Docker, нет сети, нет PHP | проверено |

### Вариант 1 — GitHub-репозиторий с CI. Главный и самый эффективный

Это снимает основную причину ошибок целиком.

**Как работает.** Проект лежит в репозитории на GitHub. Я пушу ветку — GitHub
Actions на своих раннерах (у них полный доступ в сеть) ставит зависимости,
поднимает MySQL, гоняет тесты, собирает образы и фронтенд. Я читаю результат
через API, чиню, пушу снова. Всё это без вашего участия: вы видите уже зелёный
результат и осмысленный pull request.

**Что нужно от вас:**

1. Создать приватный репозиторий.
2. Выдать fine-grained personal access token **только на этот репозиторий**,
   права: Contents — read/write, Pull requests — read/write, Actions — read.
   Ничего сверх этого не нужно.
3. Положить `ODDS_API_KEY` в Secrets репозитория. Я его не увижу: в логах
   GitHub маскирует секреты, а в коде он читается из окружения.

**Границы.** Токен не даёт доступа к другим вашим репозиториям и к аккаунту.
Отозвать можно в любой момент одной кнопкой. Ветку `main` имеет смысл защитить
правилом, чтобы я не мог пушить в неё напрямую — только через pull request,
который вы просматриваете.

**Что это даёт по каждому классу ошибок:**

- дефекты 2, 3, 4, 8, 9 (пять из двенадцати) отлавливались бы автоматически;
- дефект 1 поймался бы на первом же `composer install` в CI;
- дефекты 10 и 11 — контрактными тестами на живом API по расписанию.

### Вариант 2 — расширить сетевой доступ моей среды

Если у вас есть доступ к настройкам организации Claude (Admin settings →
Capabilities → сетевой доступ), можно добавить в разрешённые
`repo.packagist.org`, `registry.npmjs.org`, `registry-1.docker.io`. Тогда я ставлю
зависимости и гоняю тесты прямо здесь, без промежуточного звена в виде GitHub.
Цикл проверки становится секундами вместо минут.

Это не замена первому варианту, а дополнение: CI всё равно нужен как независимая
проверка на чистом окружении. Но для быстрой итерации разница огромная.

### Вариант 3 — доступ браузера к сайтам-источникам

Разрешение для встроенного браузера на `ufc.com` и `the-odds-api.com` со
scope «site». Это позволит мне **самому смотреть живую разметку** и подбирать
CSS-селекторы, а не писать их по памяти — именно отсюда взялось предупреждение
«селекторы нужно проверить на живом сайте», которое так и осталось невыполненным.

WebFetch уже читает ufc.com, но отдаёт текст без классов — для селекторов нужен
именно браузер с доступом к DOM.

### Чего не дадут доступы к папкам

Расширение доступа к папкам на Маке ничего не меняет: в изолированной Linux-VM,
через которую я работаю с вашими файлами, нет ни Docker, ни сети, ни PHP.
Ваш локальный Docker-демон мне недоступен принципиально — и это нормально,
его роль в проверках берёт на себя CI.

### Минимальный рабочий набор

Если делать что-то одно — делайте **вариант 1**. Если два — добавьте **вариант 3**,
он закрывает самую хрупкую часть проекта.

## Часть 3. Принципы работы

### 3.1. Вертикальные срезы вместо слоёв

Каждый этап — работающий кусок от базы до экрана, который можно потрогать
руками. Не «сначала все модели, потом все контроллеры»: при таком делении
ничего нельзя проверить до самого конца, а это ровно то, что уже привело
к проблемам.

### 3.2. Определение готовности

У каждого этапа есть список проверок. Этап не считается сделанным, пока
проверки не пройдены, и **следующий этап не начинается**. Большая часть
проверок автоматические — это условие, а не пожелание.

### 3.3. Сначала контракт, потом код

Для всего, что приходит извне — ufc.com, The Odds API, страницы результатов —
порядок такой:

1. Получить реальный ответ.
2. Сохранить его в репозиторий как фикстуру.
3. Написать тест, который разбирает фикстуру и проверяет разобранное.
4. Только теперь писать код разбора.

Дефекты 10 и 11 (ничья и тотал 4.5) невозможны при таком порядке: оба видны
в первом же реальном ответе.

Отдельно — **контрактный тест по расписанию**: раз в сутки CI ходит к живому
источнику и сверяет структуру ответа с фикстурой. Изменилась разметка ufc.com
или формат API — узнаём из упавшей сборки, а не из пустого экрана через месяц.

### 3.4. Ядро без фреймворка

Единственная часть первой версии, которая ни разу не сломалась, — классы модели
на чистом PHP, с автономной проверкой без composer и базы. Этот приём
сохраняется и расширяется: вся математика и все правила живут в классах
без зависимостей.

### 3.5. Не менять умолчания под работающей системой

Порты, имена, пути записываются явно в конфигурацию пользователя при первой
настройке. Любые последующие изменения умолчаний не должны трогать то,
что уже работает. Генераторы конфигов только дополняют файлы, никогда
не перезаписывают.

### 3.6. Один этап — один pull request

Изменения приезжают порциями, каждая с зелёным CI. Если что-то сломалось,
понятно, какая порция виновата, и её можно откатить целиком.

## Часть 4. Архитектура

### 4.1. Слои

```
Domain          чистый PHP, ноль зависимостей
                модель прогноза, критерий Келли, правила расчёта ставок
                    ↑
Application     сценарии: «рассчитать прогнозы турнира», «загрузить коэффициенты»
                оркестрация, транзакции, единицы работы
                    ↑
Infrastructure  адаптеры: БД, HTTP-источники, кэш, файлы
                реализации портов, объявленных в Application
                    ↑
Interface       REST API, artisan-команды, планировщик, фронтенд
```

Правило зависимостей одно: стрелки только снизу вверх. Domain не знает ни о ком.

### 4.2. Порты и адаптеры для внешних данных

В первой версии этот приём применялся только к коэффициентам (`OddsProvider`)
и оказался единственным местом, где замена источника ничего не ломает.
Распространяем на всё внешнее:

| Порт | Смысл | Адаптеры |
|---|---|---|
| `EventSource` | расписание турниров и карды | ufc.com, ручной ввод, фикстура |
| `FighterSource` | карточки и статистика бойцов | ufc.com, Sherdog, ручной ввод |
| `OddsSource` | котировки | The Odds API, ручной ввод, фикстура |
| `ResultSource` | результаты боёв | ufc.com, Sherdog, поиск, ручной ввод |

У каждого порта обязателен адаптер «фикстура» — он используется в тестах
и позволяет разрабатывать всё, что выше, не завися от живого сайта.
И обязателен адаптер «ручной ввод»: система должна оставаться полностью
работоспособной, когда все парсеры сломаны.

### 4.3. Что меняется в модели данных

Схема первой версии в целом оказалась удачной, менять её целиком незачем.
Точечные исправления:

- **`market` и `selection` — строки, а не enum.** Добавление рынка не должно
  требовать миграции с `ALTER`.
- **Тотал раундов — произвольная линия.** Вероятности хранятся картой
  «линия → over/under», а не двумя колонками под 2.5.
- **Никаких одноимённых колонок в связанных таблицах** там, где их приходится
  соединять. `fights.status` и `events.status` дали дефект 3; в v2 это
  `fights.bout_status` и `events.event_status`. Правило квалифицировать колонки
  остаётся, но лучше не создавать ловушку вовсе.
- **Импортёры идемпотентны.** Повторный запуск не плодит дубликатов и не теряет
  ручные правки — ключ уникальности продуман заранее.

### 4.4. Конфигурация

Одна точка истины на каждый параметр. Значения, от которых зависит окружение
пользователя (порты, пути), записываются в его конфиг явно при установке.
Значения предметной области (веса модели, пороги) живут в одном файле
и переопределяются через настройки в интерфейсе.

## Часть 5. ТЗ по этапам

Одиннадцать этапов. У каждого — цель, объём, чего в нём **нет**, и определение
готовности. Порядок не произвольный: каждый следующий опирается на проверенный
предыдущий.

---

### Этап 0. Каркас и конвейер проверок

**Цель:** возможность выполнять и проверять код. Всё остальное бессмысленно
до этого.

**Объём:**

- Репозиторий на GitHub, ветка `main` защищена.
- Скелет Laravel + Vue, Docker Compose, Makefile — без бизнес-логики.
- GitHub Actions:
  - `backend` — установка зависимостей, статический анализ, юнит-тесты на SQLite;
  - `frontend` — установка, сборка, проверка типов;
  - `stack` — сборка образов, подъём Compose, ожидание готовности, миграции,
    запрос к `/up`, прогон `make doctor`;
  - `contract` — по расписанию, обращение к живым источникам, сверка с фикстурами.
- `make doctor` в минимальном виде.

**Чего в этапе нет:** ни одной строки предметной логики.

**Готово, когда:**

- [ ] сборка `stack` поднимает приложение с нуля на чистой машине и получает 200 от `/up`;
- [ ] все четыре сборки зелёные;
- [ ] `make setup` на вашей машине даёт тот же результат, что CI;
- [ ] `make doctor` отрабатывает и печатает параметры подключения;
- [ ] пуш в `main` напрямую невозможен.

**Почему это первым:** дефекты 2, 8 и 9 — ошибки именно инфраструктуры, и все
три ловятся сборкой `stack` автоматически.

---

### Этап 1. Ядро модели прогнозирования

**Цель:** математика, которую можно проверить без базы, сети и фреймворка.

**Объём:**

- DTO профиля бойца и контекста боя.
- Сравнение по показателям, веса, свёртка в балл, сигмоида.
- Экспертные правила — каждое отдельным классом с собственным тестом.
- Оценка метода победы и тотала для произвольной линии.
- Текстовое объяснение прогноза.
- Автономная проверка без composer.

**Чего в этапе нет:** базы данных, HTTP, Laravel.

**Готово, когда:**

- [ ] покрытие ядра тестами не ниже 90%;
- [ ] выполняются три инварианта: симметрия при перестановке бойцов,
      ровно 50/50 у одинаковых бойцов, сумма весов равна 1.0;
- [ ] каждое экспертное правило имеет тест, который падает при его выключении;
- [ ] вероятности всех наборов исходов дают в сумме единицу;
- [ ] автономная проверка проходит без окружения.

---

### Этап 2. Хранилище и импорт из фикстур

**Цель:** схема БД и возможность наполнить её без единого обращения в сеть.

**Объём:**

- Миграции всех таблиц.
- Модели и связи.
- Фикстуры: один полный турнир с картой боёв, карточками бойцов
  и историей их поединков — снятые с реальных данных.
- Импортёр из фикстур.
- Сборка прогноза из данных БД (профиль бойца собирается из истории боёв).

**Чего в этапе нет:** парсеров, HTTP, интерфейса.

**Готово, когда:**

- [ ] `make fresh` наполняет базу из фикстур на чистом томе;
- [ ] повторный импорт не создаёт дубликатов;
- [ ] прогноз считается по данным из базы и совпадает с прогнозом
      по тем же данным, поданным напрямую в ядро;
- [ ] есть тест на каждый запрос со связыванием таблиц (это ловит дефект 3);
- [ ] полнота данных считается корректно и снижает уверенность при пробелах.

---

### Этап 3. Источник данных UFC

**Цель:** расписание, карды и карточки бойцов с живого сайта.

**Объём:**

- Порт `EventSource` и `FighterSource`, адаптер под ufc.com.
- Единая точка сетевых обращений: кэш, паузы, дневные квоты, `robots.txt`.
- Все селекторы в одном месте.
- Ручной ввод как полноценный адаптер.

**Чего в этапе нет:** коэффициентов, ставок.

**Готово, когда:**

- [ ] селекторы **проверены на живой странице** через браузер, а не по памяти;
- [ ] разбор сохранённой фикстуры даёт ожидаемый результат в тесте;
- [ ] контрактная сборка по расписанию сверяет живую страницу со структурой фикстуры;
- [ ] при неразобранной странице пишется внятное предупреждение, а не пустой результат;
- [ ] лимиты обращений соблюдаются, что подтверждено тестом;
- [ ] загрузка ближайшего турнира даёт полный кард с корректными именами.

---

### Этап 4. Коэффициенты

**Цель:** котировки, привязанные к правильным бойцам.

**Объём:**

- Порт `OddsSource`, адаптер The Odds API.
- Разбор всех рынков, встречающихся в реальных ответах: победа, ничья,
  тотал с любой линией, метод победы. Неизвестные рынки — игнорируются явно.
- Сопоставление с боями по всем ближайшим турнирам за один запрос.
- Выравнивание порядка бойцов.
- Версионирование котировок.
- Ручной ввод.
- Диагностическая команда, объясняющая нулевой результат.

**Чего в этапе нет:** ставок и банкролла.

**Готово, когда:**

- [ ] фикстура — **реальный полный ответ API**, включая `h2h_lay`, ничью и тотал 4.5;
- [ ] тест: коэффициент фаворита привязан к фавориту при любом порядке бойцов;
- [ ] тест: неизвестные рынки не сохраняются и не ломают разбор;
- [ ] несопоставленные пары считаются по всем турнирам, а не по одному;
- [ ] диагностическая команда различает пять причин нулевого результата;
- [ ] дневная квота не превышается, что подтверждено тестом.

---

### Этап 5. Прогнозы на реальных данных

**Цель:** соединение ядра с базой и котировками.

**Объём:**

- Сценарий «рассчитать прогноз боя», версионирование прогнозов.
- Учёт очной встречи, высоты, титульного статуса.
- Сопоставление рынков букмекера с вероятностями модели.

**Готово, когда:**

- [ ] для каждой сохранённой котировки модель даёт вероятность либо явно
      сообщает, что этот рынок не оценивает;
- [ ] пересчёт помечает прежние прогнозы неактуальными;
- [ ] объяснение прогноза читается и соответствует числам.

---

### Этап 6. Ставки и банкролл

**Цель:** рекомендации и виртуальные деньги.

**Объём:** поиск value, критерий Келли с ограничениями, лимит на бой,
размещение, история банкролла.

**Готово, когда:**

- [ ] формулы EV и Келли проверены на эталонных значениях;
- [ ] проверено каждое ограничение: потолок, пол, множитель уверенности,
      лимит на бой, диапазон коэффициентов;
- [ ] банкролл сходится: сумма операций равна текущему балансу;
- [ ] размещение ставки при нехватке средств не уводит баланс в минус.

---

### Этап 7. Результаты и расчёт ставок

**Готово, когда:**

- [ ] расчёт покрыт тестами для всех рынков: выигрыш, проигрыш, возврат;
- [ ] несостоявшийся бой возвращает ставку по всем рынкам;
- [ ] ничья на рынке победы — возврат;
- [ ] нехватка данных даёт возврат, а не проигрыш;
- [ ] ручной ввод результата пересчитывает банкролл.

---

### Этап 8. Статистика и бэктест

**Готово, когда:**

- [ ] метрики совпадают с посчитанными вручную на контрольном наборе;
- [ ] бэктест не подглядывает в будущее — есть тест, что профиль бойца
      на дату боя не содержит более поздних боёв;
- [ ] сравнение со стратегиями «фаворит» и «случайный выбор» воспроизводимо.

---

### Этап 9. Интерфейс

**Готово, когда:**

- [ ] сборка фронтенда проходит в CI;
- [ ] сквозной тест: открыть дашборд, перейти к бою, увидеть прогноз;
- [ ] обе темы, только русский язык;
- [ ] пустые состояния объясняют, что делать.

### Этап 10. Эксплуатация

**Объём:** планировщик, логи, `make doctor` в полном виде, документация.

**Готово, когда:**

- [ ] полный цикл отрабатывает по расписанию без вмешательства;
- [ ] `make doctor` ловит все известные классы поломок;
- [ ] документация описывает каждый шаг установки, проверенный на чистой машине.

## Часть 6. Система проверок

Пять уровней, от самого быстрого к самому медленному.

| Уровень | Что проверяет | Где выполняется | Время |
|---|---|---|---|
| Автономная проверка | математика ядра | где угодно, без зависимостей | секунда |
| Юнит-тесты | классы предметной области | CI, локально | секунды |
| Контрактные тесты | разбор реальных ответов внешних источников | CI на фикстурах | секунды |
| Тесты API | эндпоинты с базой | CI на SQLite и MySQL | десятки секунд |
| Сборка стека | Docker целиком, миграции, `/up`, `make doctor` | CI | минуты |
| Живые контракты | структура ответов живых источников | CI по расписанию | минуты |

Отдельно стоит выделить **живые контракты** — единственный уровень, который
ловит изменения на стороне ufc.com и букмекеров. Без него проект тихо ломается
между запусками, и это ровно то, что случилось бы с текущей версией.

### Инварианты, которые стерегутся всегда

1. Перестановка бойцов даёт зеркальные вероятности.
2. Одинаковые бойцы — ровно 50/50.
3. Сумма весов факторов равна 1.0.
4. Вероятности внутри набора исходов дают единицу.
5. Сумма операций банкролла равна текущему балансу.
6. Повторный импорт не меняет состояние базы.

## Часть 8. Риски

| Риск | Насколько вероятен | Что делаем |
|---|---|---|
| ufc.com меняет разметку | высокий, несколько раз в год | живые контрактные тесты, селекторы в одном месте, ручной ввод как запасной путь |
| Бесплатная квота API исчерпана | средний | учёт квоты, кэш, один запрос на все турниры |
| Модель не превосходит букмекера | высокий | это ожидаемо; бэктест и сравнение с бенчмарками покажут честно, без самообмана |
| Данных по бойцу не хватает | постоянный | полнота данных снижает уверенность, предупреждение в объяснении |
| Ошибка в расчёте банкролла | средний | инвариант «сумма операций равна балансу» проверяется тестом |

Про предпоследний пункт стоит сказать прямо: букмекеры закладывают маржу 5–8%,
и их линия обычно точнее одиночной статистической модели. Стабильный
положительный ROI на дистанции — сложная задача, а не свойство хорошо
написанного кода. Задача проекта — честно измерять, а не обещать.
