# Настройка модели прогнозирования

Модель живёт в `backend/app/Services/Prediction`. Все числа вынесены в
`backend/config/ufc.php` — правка кода нужна только для новых правил и показателей.

## Сначала прочитать

Порядок расчёта в `PredictionEngine::predict()`:

```
факторы (FactorCalculator)
  → взвешенная сумма, балл в [-1, 1]
  → сигмоида: P = 1 / (1 + exp(-score × score_scale))
  → экспертные правила (ExpertRules), в пунктах вероятности
  → очная встреча, вес 0.15
  → границы 5%…95%
  → метод победы и тотал (MethodEstimator)
  → объяснение (ExplanationBuilder)
```

**Важно:** правила применяются после сигмоиды, а не до неё, хотя ТЗ описывает
обратный порядок. Причина в README, раздел «Одно осознанное отступление от ТЗ».
Не переставляйте это обратно, не обсудив с владельцем.

## Что и где менять

| Задача | Место |
|---|---|
| Веса показателей | `config/ufc.php` → `weights` (сумма ровно 1.0) |
| Разброс вероятностей | `config/ufc.php` → `score_scale` (по умолчанию 3.5) |
| Границы вероятности | `config/ufc.php` → `probability_bounds` |
| Параметры правил | `config/ufc.php` → `expert_rules` |
| Выключить правило | там же, `enabled => false` |
| Формулы сравнения | `FactorCalculator::calculate()` |
| Новое правило | `ExpertRules` + запись в `config/ufc.php` |
| Метод победы, тотал | `MethodEstimator` + `config/ufc.php` → `method` |
| Расчёт формы по боям | `FighterProfileBuilder` + `config/ufc.php` → `form` |

Часть параметров пользователь меняет через интерфейс («Настройки» → веса модели).
Они хранятся в таблице `settings` и перекрывают файл; актуальный набор собирает
`SettingsRepository::domainConfig()`. Если добавляете новый настраиваемый параметр,
пропишите его в `SettingsRepository::definitions()` и в валидацию
`SettingsController::update()`, иначе он молча не сохранится.

## Как добавить экспертное правило

1. **Конфигурация** — в `config/ufc.php`, секция `expert_rules`:

```php
'reach_advantage' => [
    'enabled' => true,
    'min_difference_cm' => 12,
    'adjustment' => 0.03,   // в пунктах вероятности, не в баллах
],
```

2. **Логика** — в `ExpertRules`. Два места на выбор:

- `evaluateForFighter()` — правило про одного бойца относительно соперника.
  Вызывается дважды, для обеих сторон; знак корректировки метод `apply()`
  переставляет сам, внутри всегда возвращайте положительное значение «в пользу
  того, о ком речь».
- `evaluateSymmetric()` — правило, сравнивающее бойцов между собой (левша, возраст,
  высота, опыт титульников). Вызывается один раз, знак определяете сами.

Возвращайте массив строго такой формы:

```php
[
    'key' => 'reach_advantage',
    'label' => 'Преимущество в размахе рук',
    'adjustment' => (float) $rule['adjustment'],
    'target' => $side,
    'description' => sprintf('У %s размах больше на %d см.', $self->name, $gap),
]
```

`description` попадает в объяснение прогноза и в интерфейс — пишите его законченным
предложением по-русски и в именительном падеже для имён (склонять имена бойцов
нельзя, они приходят как есть).

3. **Получите параметры через `$this->rule('key')`** — этот помощник сам вернёт
`null`, если правило выключено.

4. **Тест** — обязательно, в `tests/Unit/PredictionEngineTest.php`. Шаблон: берём
двух одинаковых бойцов (`$this->wrestler()` и его клон), меняем одно поле и
проверяем, что правило сработало и вероятность сдвинулась в нужную сторону:

```php
public function test_reach_advantage_rule(): void
{
    $long = $this->wrestler(['reach_cm' => 200]);
    $short = $this->wrestler(['id' => 9, 'name' => 'Клон']);

    $prediction = $this->engine()->predict($long, $short, new FightContext);

    $this->assertContains('reach_advantage', array_column($prediction->appliedRules, 'key'));
    $this->assertGreaterThan(0.5, $prediction->probabilityFighter1);
}
```

## Как менять веса

Веса нормируются к сумме 1.0 автоматически (`SettingsRepository::normalizeWeights`),
но в `config/ufc.php` держите их уже сходящимися к единице — так понятнее читать.

Ориентиры, проверенные тестами:

- сумма весов факторов в трёхраундовом бою равна 1.0 (в пятираундовом кардио
  получает множитель 1.4, и балл нормируется на фактическую сумму);
- одинаковые бойцы должны давать ровно 50/50 — если нет, где-то асимметрия;
- перестановка бойцов местами даёт зеркальные вероятности.

`score_scale` управляет тем, насколько уверенно модель говорит. При 3.5 разрыв
в статистике на 30% даёт примерно 74%. Увеличивать выше 5 не стоит: модель начнёт
выдавать 90% там, где данных на это не хватает.

## Обязательная проверка после любой правки

По возрастанию тяжести:

```bash
make selfcheck     # 26 проверок, секунда, без Docker
make test-unit     # юнит-тесты модели и ставок
make test          # весь набор
```

`make selfcheck` печатает вероятность и объяснение для эталонной пары
«борец против ударника» — удобно смотреть глазами, насколько правка сдвинула оценку.

## Проверка на истории

Бэктест пересчитывает прогноз «на дату боя»: в профиль бойца попадают только бои,
состоявшиеся раньше, — подглядывания в будущее нет.

```bash
make backtest FROM=2024-01-01 TO=2025-12-31 BANKROLL=10000
```

Нужны прошедшие бои с результатами **и** сохранёнными котировками. Если их нет,
бэктест честно скажет «нет исторических боёв» — сначала наполните базу.

На что смотреть в отчёте:

| Показатель | Что означает |
|---|---|
| Точность прогнозов | доля угаданных победителей; ниже 60% — модель не лучше монетки с учётом фаворитов |
| ROI | главный показатель; на дистанции менее 100 ставок это шум, а не результат |
| Максимальная просадка | если больше 40%, уменьшите `kelly_fraction` до 0.5 |
| Ставок сделано | меньше 30 — выводы делать рано |

Калибровку смотрите в интерфейсе: «Статистика» → «Калибровка прогнозов».
Столбцы должны идти близко к диагонали: среди боёв, где модель дала 70%,
победитель должен угадываться примерно в 70% случаев. Систематический перекос
вверх означает, что `score_scale` завышен.

## Здравый смысл

- Не подгоняйте веса под конкретный турнир — это переобучение на шуме.
- Улучшение ROI на выборке в 20 ставок ничего не значит.
- Букмекерская линия обычно точнее одиночной модели: если ваш ROI на истории
  выше 15%, скорее всего в данные просочилось будущее — проверьте, что котировки
  сохранены с датой до боя, а профиль строится с `asOf`.
- Не убирайте снижение уверенности при неполных данных: это защита от уверенных
  прогнозов на пустом месте.
