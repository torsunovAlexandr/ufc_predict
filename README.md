# UFC Predict — прогнозирование боёв и виртуальные ставки

Персональное веб-приложение: собирает статистику бойцов UFC, считает вероятности исходов
по гибридной экспертно-статистической модели, ищет value-ставки по букмекерским
коэффициентам и ведёт виртуальный банкролл в рублях.

Реальные деньги нигде не используются — весь банк виртуальный.

---

## Быстрый старт

Нужен только Docker (Desktop или Engine + Compose v2).

```bash
cd "ufc predict"
make setup
```

`make setup` создаст `backend/.env`, соберёт фронтенд и поднимет контейнеры.
`make` без аргументов показывает список всех команд.

То же самое вручную, если make недоступен:

```bash
cp backend/.env.example backend/.env
docker compose --profile build run --rm node   # сборка фронтенда
docker compose up -d
```

Приложение откроется на **http://localhost:8080**.

При первом запуске контейнер `php` сам поставит зависимости composer, сгенерирует ключ,
накатит миграции и наполнит базу демонстрационными данными — интерфейс будет живым
сразу, ещё до первой загрузки с ufc.com.

Полезные команды:

```bash
make            # список всех команд с описаниями
make logs       # логи бекенда
make pipeline   # полный цикл обновления данных и прогнозов
make predict    # только пересчитать прогнозы и рекомендации
make results    # получить результаты и рассчитать ставки
make test       # тесты
make down       # остановить
make reset      # остановить и удалить базу (с подтверждением)
```

### Подключение к базе из PhpStorm и других клиентов

```bash
make db-info      # напечатает готовые параметры
```

| Параметр | Значение |
|---|---|
| Хост | `127.0.0.1` |
| Порт | `3306` (меняется переменной `DB_PORT_EXTERNAL`) |
| База | `ufc_predict` |
| Логин / пароль | `ufc` / `secret` (или ваши из `backend/.env`) |

Частая путаница: в `backend/.env` стоят `DB_HOST=mysql` и `DB_PORT=3306` — **это адрес
внутри docker-сети**, по которому контейнер бекенда находит контейнер базы. С вашей
машины имя `mysql` не резолвится; снаружи нужен `127.0.0.1` и тот порт, который
опубликован в `docker-compose.yml`. Именно `127.0.0.1`, а не `localhost`: некоторые
клиенты сначала пробуют IPv6-адрес `::1`, куда Docker порт не публикует.

Если порт 3306 уже занят локально установленным MySQL, задайте другой в корневом `.env`:

```
DB_PORT_EXTERNAL=33061
```

и выполните `make up` — контейнер пересоздастся с новым портом, данные останутся.

### Два файла .env — зачем

- `backend/.env` — настройки приложения. **Это источник истины**, правьте только его.
- `.env` в корне — переменные для Docker Compose (параметры контейнера MySQL).
  Создаётся командой `make env` из `backend/.env` и в репозиторий не коммитится.

`make up`, `make setup`, `make restart` и `make rebuild` синхронизируют корневой `.env`
автоматически, так что пароли приложения и базы не разойдутся. Если поднимаете
проект напрямую через `docker compose up`, выполните перед этим `make env`.

Пароль базы MySQL запоминает при первой инициализации тома. Если вы поменяли
`DB_PASSWORD` уже после первого запуска, том придётся пересоздать:
`docker compose down -v && make setup`.

### Если что-то не поднялось

Первым делом — статус и логи конкретного контейнера:

```bash
docker compose ps                 # кто упал и с каким кодом
docker compose logs mysql         # логи MySQL
docker compose logs php           # логи бекенда
docker compose logs --tail=50 mysql
```

| Симптом | Причина и что делать |
|---|---|
| `mysql` в цикле `Restarting`, в логе `unknown variable` | В `docker/mysql/my.cnf` попала переменная, удалённая в MySQL 8.4. Уберите строку, затем `docker compose down -v && make up` — том с недоинициализированной базой нужно снести. |
| `mysql` пишет `Access denied for user` при старте `php` | Пароли в `backend/.env` и в томе MySQL разошлись. Том хранит те, с которыми база инициализировалась в первый раз: `docker compose down -v && make setup`. |
| `php` не дожидается базы, миграции не накатились | `make migrate` вручную после того, как `docker compose ps` покажет `mysql (healthy)`. |
| `Connection refused` при подключении из PhpStorm | Порт или хост не те. `make db-info` покажет верные; из GUI-клиента это всегда `127.0.0.1`, а не `mysql` из `backend/.env`. |
| Порт 8080 занят | `APP_PORT=8090 docker compose up -d` |
| Порт 3306 занят локальным MySQL | Добавьте `DB_PORT_EXTERNAL=33061` в корневой `.env` и `make up` |
| Пустая страница на localhost:8080 | Фронтенд не собран: `make front` |

Важно про том с данными: MySQL инициализирует базу **только при первом запуске
с пустым томом**. Если первый запуск не удался, простой перезапуск ничего не починит —
нужно `docker compose down -v`, чтобы удалить том и дать базе создаться заново.
Виртуальные ставки при этом пропадут, прогнозы пересчитаются командой `make predict`.

### Про парсинг ufc.com — важное

Селекторы написаны по актуальной на момент разработки вёрстке ufc.com, но проверить их
на живом сайте из среды разработки было нельзя (нет сетевого доступа). Вёрстка UFC
меняется несколько раз в год, поэтому первый запуск парсера может ничего не найти —
это ожидаемо и лечится за пять минут.

Что делать, если `ufc:sync-events` вернул ноль турниров:

1. Открыть https://www.ufc.com/events, посмотреть в инспекторе классы карточек.
2. Поправить константы в начале `backend/app/Services/Scraping/UfcEventScraper.php`
   (`EVENT_CARD_SELECTORS`, `EVENT_LINK_SELECTORS`, `FIGHT_SELECTORS`) и
   `UfcFighterScraper.php` — все селекторы собраны там в одном месте.
3. Повторить: `docker compose exec php php artisan ufc:sync-events --fights --force`.
4. Подробности разбора пишутся в `backend/storage/logs/scraping-*.log`.

Пока парсер не настроен, система полностью работоспособна: бойцов, коэффициенты
и результаты можно вводить вручную через интерфейс.

### Про парсинг сайтов букмекеров

`SCRAPER_MARATHONBET_ENABLED` и `SCRAPER_1XBET_ENABLED` по умолчанию `false`.
Причины: линия у большинства БК подгружается скриптами (простой HTML-парсер её не увидит),
а правила сайтов обычно прямо запрещают автоматический сбор данных. Основной путь —
The Odds API (бесплатный ключ на https://the-odds-api.com) или ручной ввод.
Ограничение «не чаще 1 запроса в 10 минут на сайт» в коде соблюдается.

## Как работает модель

Порядок расчёта (раздел 4 ТЗ) реализован в `PredictionEngine::predict()`:

1. **Сравнение по показателям** — `FactorCalculator`.
   Для каждой группы считается `advantage = (v1 − v2) / (v1 + v2 + ε)` в диапазоне [−1, 1].
   Внутри группы может быть несколько метрик: например, «борьба в атаке» —
   это объём тейкдаунов (70%) плюс их реализация (30%).
2. **Веса** — из `config/ufc.php`, сумма ровно 1.0. В пятираундовых боях вес кардио
   автоматически повышается в 1.4 раза, а итоговый балл нормируется на сумму
   фактически применённых весов, чтобы остаться в [−1, 1].
3. **Сигмоида**: `P = 1 / (1 + exp(−score × score_scale))`, по умолчанию `score_scale = 3.5`.
4. **Экспертные правила** — `ExpertRules`: борец против слабой защиты от тейкдаунов,
   ударник против борца, левша, разница в возрасте, серия нокаутов, отсутствие опыта
   пяти раундов, высота над уровнем моря, опыт титульных боёв.
5. **Очная встреча** с весом 0.15, со сжатием к 50/50 при единственной прошлой встрече.
6. **Границы** 5%…95% и расчёт уверенности с поправкой на полноту данных.
7. **Метод победы и тотал раундов** — `MethodEstimator`.
8. **Объяснение на русском** — `ExplanationBuilder`.

### Одно осознанное отступление от ТЗ

В ТЗ экспертные корректировки применяются к баллу *до* сигмоиды, но сами правила
сформулированы в процентах вероятности («повышается на 5–10%»). Это несовместимо:
одна и та же добавка к баллу даёт разный прирост вероятности в зависимости от того,
где мы находимся на сигмоиде — у равного боя это +12 п.п., у разгромного +2 п.п.

Поэтому корректировки применяются **после** сигмоиды, в пунктах вероятности:
«+7.5%» означает ровно +7.5 п.п., результат гарантированно остаётся в границах,
а балл для хранения пересчитывается обратно через логит. Формулы шагов 1, 2 и 4
при этом полностью соответствуют ТЗ.

## Управление ставками

- **Value**: `EV = P × K − 1`, порог по умолчанию 0.05 (настраивается).
- **Размер**: `f = (P × K − 1) / (K − 1)`, затем множитель уверенности
  (×1.2 при P > 0.65, ×0.8 при P < 0.55), потолок 5% банка (10% при P > 0.8),
  пол 0.5%, округление до рубля.
- **Несколько ставок на бой**: суммарно не более 10% банка, приоритет — по убыванию EV.
  Если лимит выбран частично, следующая ставка урезается до остатка.
- **Расчёт**: по результату боя. Ничья без рынка «ничья» и NC — возврат.
  Тотал «больше 2.5» выигрывает, если бой длился дольше 750 секунд чистого времени.

## Команды artisan

```bash
php artisan ufc:sync-events --fights   # турниры и карды с ufc.com      (make events)
php artisan ufc:sync-fighters          # карточки бойцов                (make fighters)
php artisan ufc:sync-odds              # коэффициенты                   (make odds)
php artisan ufc:predict --recommend    # прогнозы + рекомендации        (make predict)
php artisan ufc:results                # результаты и расчёт ставок     (make results)
php artisan ufc:pipeline               # всё перечисленное подряд       (make pipeline)
php artisan ufc:backtest --from=2024-01-01   # прогон на истории        (make backtest FROM=2024-01-01)
```

Контейнер `scheduler` выполняет `schedule:work` и запускает эти команды сам:
турниры раз в 6 часов, бойцы ночью, коэффициенты и прогнозы каждые 6 часов,
результаты в 9 утра. Расписание — в `backend/routes/console.php`.

### Соблюдение лимитов из ТЗ

Всё сосредоточено в `HttpFetcher`:

- кэш страниц в таблице `scrape_logs`, по умолчанию 24 часа;
- пауза между запросами к одному источнику (3 сек для ufc.com, 5 для Sherdog);
- полное обновление источника не чаще раза в 3 часа (`canRefreshSource`);
- учёт дневных квот API (`requestsToday`) — 500 для The Odds API, 100 для Google CSE;
- разбор и соблюдение `robots.txt`;
- для парсеров БК — блокировка на 10 минут через кэш.

Состояние всех источников видно на странице «Настройки».

## API

Приложение персональное и работает **без авторизации** — оно рассчитано на запуск
на локальной машине. Если понадобится выставить его наружу, достаточно навесить
middleware на группу маршрутов в `backend/routes/api.php`.

Основные эндпоинты:

```
GET  /api/dashboard                     сводка, ближайшие бои, рекомендации
GET  /api/events?scope=upcoming|past    список турниров
GET  /api/events/{id}                   турнир с картой боёв
POST /api/events/{id}/predict           пересчитать прогнозы турнира
POST /api/events/{id}/odds              обновить коэффициенты
POST /api/events/{id}/results           получить актуальные результаты
GET  /api/fights/{id}                   бой: прогноз, котировки, ставки, результат
POST /api/fights/{id}/predict           пересчитать прогноз
POST /api/fights/{id}/odds              ручной ввод коэффициентов
POST /api/fights/{id}/result            ручной ввод результата
GET  /api/statistics/summary            профит, ROI, серии
GET  /api/statistics/bankroll           точки графика банкролла
GET  /api/statistics/benchmarks         сравнение с простыми стратегиями
GET  /api/statistics/accuracy           точность и калибровка прогнозов
GET  /api/settings   PUT /api/settings  настройки
POST /api/backtest                      прогон на истории
```

## Структура базы данных

Таблицы соответствуют разделу 3 ТЗ: `fighters`, `events`, `fights`, `fighter_stats`,
`odds`, `predictions`, `bets`, `results`, `bankroll_history`, `settings`.
Добавлена служебная `scrape_logs` — кэш страниц и учёт лимитов запросов.

Разделение `predictions` / `bets`: прогноз хранит вероятности, факторы и объяснение
по бою, а каждая рекомендованная или размещённая ставка — отдельная строка в `bets`
(на один бой их может быть несколько: победа, тотал, метод).

Кардио считается из `fighter_stats`: сравнивается плотность значимых ударов
в первых двух раундах и в третьем и далее (колонки `*_early` / `*_late`).

## Ограничения, о которых стоит знать

- **Модель нужно откалибровать на истории.** Веса из ТЗ — разумная отправная точка,
  но их стоит проверить бэктестом на реальных данных за пару лет и подправить
  на странице «Настройки». До накопления истории относитесь к процентам как
  к ориентиру, а не к истине.
- **Букмекеры закладывают маржу 5–8%**, и их линия обычно точнее одиночной модели.
  Стабильный положительный ROI на дистанции — сложная задача, а не данность.
- **Данных по бойцам часто не хватает** (дебютанты, бойцы из других промоушенов).
  Модель считает полноту данных и снижает уверенность, а в объяснении появляется
  предупреждение — не игнорируйте его.
- Вероятность ничьей в модели равна нулю: в UFC ничьи редки (менее 0.5% боёв).
  Ставки на ничью не рекомендуются, а при ничьей ставка на победителя возвращается.
